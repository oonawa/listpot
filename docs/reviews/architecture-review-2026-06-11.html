プロダクトの性質と、それに対する適性

「りすとぽっと」は、Netflix / Prime Video / Disney+ / Hulu / U-NEXT などの配信URLから映画を1つのリストに集約し、ルーレットで観る作品を選んだり、サブリストで分類したりできるウォッチリスト管理サービスです。ユーザー1人 = 1リスト、パスワードレス認証、未ログイン時は LocalStorage で動作、という個人ユーザー向けの軽量SaaSです。

  • 適性◎：更新頻度が低く読み取り中心の個人データ → Server Components 中心・短期キャッシュと相性が良い（ただしキャッシュは未実装、後述）。
  • 適性◎：未ログイン利用を LocalStorage、ログイン利用をDBで同一インターフェースに抽象化 → プロダクトの「気軽に試せる」性質に合致。
  • 要注意：公開リスト（共有URL）という性質上、他人のIDが推測・流出しやすい → だからこそ更新系の所有権チェックが致命的に重要。

01🔐 セキュリティ

認証・暗号化・入力バリデーションの基礎は堅実に実装されています。最大の問題は、参照系には所有権チェックがあるのに更新系にはないという非対称性です。共有URLでIDが露出しやすいプロダクト特性と相まって、影響が大きくなります。

CRITICAL 更新系 Server Action の所有権チェック欠落（IDOR）

以下の更新系 Action は publicId（UUID）のみを受け取り、「そのリソースがログインユーザーのものか」を一切照合していません。他人の listItemId / publicListId / subListPublicId を知っていれば、第三者が削除・改変・追加できます。共有リスト機能でIDが他者の目に触れる本プロダクトでは、現実的な攻撃面です。

  • features/list/actions/removeListItem.ts → removeListItemService.ts → deleteListItemByPublicId(publicId)（publicId だけで DELETE）
  • features/list/actions/toggleWatchStatus.ts → toggleWatchStatusService.ts（userId 照合なし）
  • features/list/actions/storeListItem.ts → storeListItemService.ts:20 の findListIdByPublicId(publicListId)（任意リストへ追加・上書き可能）
  • features/list/actions/addSubListItem.ts / removeSubListItem.ts → manageSubListItemService.ts（subList と listItem の所有者関係を未検証）

対照（正しく書けている例）：参照系の getUserMovieList(publicListId, userId) は app/[publicListId]/page.tsx:24-30 で currentUserId() 取得後に userId を渡して照合しています。サブリストの deleteSubListService / renameSubListService も subList.listId === userListId を確認済み。つまり正しいパターンは既にコードベース内に存在しており、更新系へ横展開するだけです。

影響
第三者による他ユーザーのリストアイテム削除・既読状態改変・サブリスト汚染・任意リストへの追加。
推奨対応
各更新系 Action 冒頭で currentUserId() を取得し、service 層を userListId(userId, publicListId) 相当（所有者照合つき検索）に統一する。参照系・サブリスト削除系と同じ作法に揃える。

HIGH セキュリティヘッダが未設定

next.config.ts は devIndicators: false のみで、CSP / HSTS / X-Frame-Options / X-Content-Type-Options / Referrer-Policy などのレスポンスヘッダが設定されていません。クリックジャッキングやMIMEスニッフィング、XSSの被害拡大に対する多層防御が欠けています。

推奨対応
next.config.ts の headers() もしくは middleware で主要セキュリティヘッダを付与。最低限 X-Frame-Options: DENY / X-Content-Type-Options: nosniff / Strict-Transport-Security、可能なら CSP を導入。

HIGH テスト用の実シークレットがリポジトリにコミットされている

.env.test に JWT_SECRET / ENCRYPTION_KEY / HMAC_SECRET の具体値が含まれています。テスト専用だとしても、鍵の値がGit履歴に残るのは避けたい慣行です。万一、同じ値が他環境に流用されていれば本番影響に直結します。

推奨対応
.env.test を .gitignore 化し、CI ではダミー値を環境変数で注入。本番の鍵がこれらと共有されていないことを確認。

MEDIUM 入力バリデーションの不整合・緩さ

  • renameSubList.ts の name は z.string().min(1) のみで 最大長がない。一方 createSubList.ts は .max(50) あり → 不整合。過大ペイロード・表示崩れの余地。
  • URLは z.url() で形式検証されるが、javascript: 等のスキーム制限は明示されていない。表示時のエスケープに依存。
推奨対応
renameSubList に .max(50) を追加して createSubList と揃える。URLは許可スキーム（http/https）をホワイトリスト化。

MEDIUM レート制限のクライアントIP判定 / 依存パッケージの既知脆弱性

  • sendLoginCode.ts のレート制限は x-forwarded-for の先頭値を素朴に採用。信頼できるプロキシ前提が無いと、ヘッダ偽装でレート制限を回避され得る。
  • npm audit で HIGH 相当の指摘（@react-email/preview-server、drizzle-orm 経由の間接依存など）。多くは dev 依存だが棚卸しが必要。
推奨対応
信頼プロキシ段数を踏まえたIP抽出、または認証系は IP+メールの複合キーで制限。依存は npm audit 結果を本番/開発で切り分けて計画的に更新。

GOOD 防御の基礎は堅牢

  • メールアドレスを AES-256-GCM で暗号化し、HMAC-SHA256 で検索可能化（encryption.ts）。ログインコードは SHA-256 ハッシュ保存。
  • セッショントークンは HS256 JWT + deviceId + expiresAt を多層検証（verifySessionTokenService.ts）。アカウント削除など高リスク操作は reauth token で再認証（deleteUser.ts）。
  • 全 Server Action で Zod の safeParse による入力検証。DBアクセスは Drizzle のクエリビルダでパラメタライズド（生SQLはテストのリセット処理のみ）。
  • Cookie は httpOnly / sameSite: "lax" / 本番 secure。更新は Server Actions 経由で CSRF 耐性。Markdown は許可タグのホワイトリスト方式で dangerouslySetInnerHTML 不使用。
  • 認証コードのレート制限あり（検証10回/送信5回・15分窓、IPはHMAC保存でプライバシー配慮）。

02🏛 アーキテクチャ / ソフトウェア設計

このプロダクトの規模（個人向け軽量SaaS、開発者は少人数想定）に対して、レイヤリングと規約が過剰でも不足でもなく適切です。AIエージェント駆動の開発を意識した手順書（docs/）まで整っており、保守性が高い設計です。

GOOD Result<T> 型による統一エラーハンドリング

features/shared/types/Result.ts の判別可能ユニオンを全 Action / Service / Repository が返却。例外スローと戻り値の混在がなく、エラーコードも7種に標準化。result.success で型が絞り込まれ、data アクセスの安全性が型で保証されます。プロダクトの「失敗が普通に起こる外部連携（TMDB/メール送信）」と相性が良い選択です。

GOOD features 層の明快な単方向分割

Action（入力検証＋副作用）→ Service（業務ロジック＋認可）→ Repository（DB/外部API） の一方向依存。auth / list / movieDatabase / user / shared に機能分割され、責務境界が明確です。Repository は optional な tx を受け取る トランザクション対応設計（authTokenRepository.ts）で、同一関数を単独実行とトランザクション内の双方で再利用できます。

※ ただしセキュリティ章の通り、「認可は Service 層で行う」という規約が更新系で守られていない箇所があります。設計の型は良いので、規約の徹底が課題です。

GOOD RSC / Client Component の使い分け・LocalStorage 抽象化

  • 認可・初期データ取得は Server Component（app/layout.tsx, app/page.tsx, app/[publicListId]/page.tsx）、対話的UIは Client Component と整理されている。
  • 未ログイン（LocalStorage）とログイン（DB）を 同一シグネチャの Repository インターフェースに抽象化（useListLocalStorageRepository.ts / Jotai）。UI層の分岐が最小限で、プロダクトの「ログイン不要で試せる」要件をきれいに満たしている。

GOOD DBスキーマの正規化と開発ワークフロー

  • M:N関連（movie_directors, sub_list_items）を中間テーブル + uniqueIndex で正規化し、重複登録を制約レベルで防止。TMDBデータは movie_cache 別テーブルで TTL を制御。
  • docs/ に4フェーズTDDワークフロー（テスト計画→実装計画→TDD→検証）、コーディングスタイル、レビュー方針を明文化。Action層起点の Medium テストを中心に据える方針も明確。

MEDIUM 改善余地（保守性）

  • 認可規約の明文化と徹底：「全更新系 Action は所有権を Service 層で照合する」をワークフロー/レビュー観点に追加し、テンプレ化する（最重要課題と直結）。
  • storeListItem.ts:29 の console.error は正常系（バリデーション失敗）で本番ログに出る。開発時のみに絞るか削除。
  • ListItem 型が draft / 既読状態など多くの分岐を抱え複雑。役割別（DraftListItem / ServerListItem など）への分割を検討。
  • E2E がビルド必須で1回3分前後。globalSetup での migrate/seed 一度きり化など起動短縮の余地。

03⚡ パフォーマンス

サーバー側のデータ取得（並列化・JOIN・インデックス・接続シングルトン化）は堅実です。伸びしろはフロント配信側、特に画像最適化とページキャッシュに集中しています。映画ポスター画像を多用するプロダクトなので、画像最適化の効果は特に大きいはずです。

HIGH next/image 未使用（全て生 <img>）

映画ポスターを多数表示するにもかかわらず、ListItem/Content/Detail、SearchResult、List/Item など全て生の <img> です。withTmdbImageSize() でサイズ指定はするものの、srcset（レスポンシブ）/ WebP変換 / lazy loading / width-height によるCLS対策が無い。映画リスト中心のUIでは LCP・CLS・転送量に直結します。

推奨対応
next/image へ移行し、TMDBドメインを images.remotePatterns に登録。サイズ確定で CLS 抑制、自動 WebP/AVIF と lazy loading を享受。

HIGH ページレベルのキャッシュ戦略が無い

revalidate / "use cache" / unstable_cache がいずれも未使用で、各ページが毎リクエストで fresh にDBアクセスします。映画情報自体は6ヶ月キャッシュ（getMovieWithCacheService.ts）されている一方、ページ描画レベルのキャッシュが空白。更新頻度が低い個人リストという性質上、短期キャッシュの恩恵が大きい領域です。

推奨対応
ユーザー固有データのため長期ISRは避けつつ、共有リスト表示などに短期 revalidate やタグ無効化（revalidateTag）を導入。更新系Actionから対象タグを無効化する。

MEDIUM サブリスト周りの反復クエリ / 全件取得

  • getSubLists() → findSubListsByListId() と getCheckedSubListIds() → findCheckedSubListIdsByListId() が同一リストへ複数回アクセス。統合の余地。
  • findCheckedSubListIdsByListId() はリスト配下の全サブリストアイテムを取得するため、リスト肥大時にコスト増。
推奨対応
1回のJOINクエリへ統合、または必要列・必要範囲に絞る。Promise.all 済みの並列化はそのまま活かす。

MEDIUM クライアントバンドルと Suspense 活用

  • "use client" が約39ファイルとやや広め。motion / jotai / html-react-parser 等の同梱量を @next/bundle-analyzer で実測したい。
  • 並列クエリの結果が揃うまでページ全体がブロックされ、Suspense / streaming による段階表示が未活用。docs/frontend.md の方針（busy/loading/done）と実装の間にギャップ。
推奨対応
重いリスト領域を Suspense 境界で分割しストリーミング。dynamic import の ssr:false が本当に必要か精査。

GOOD サーバー側データ取得は堅実

  • Server Components で直接フェッチし、非依存クエリは Promise.all で並列化（app/[publicListId]/components/List/index.tsx）。
  • 複数テーブルを単一クエリの JOIN で取得（userListItemsByListId()）、重複防止 uniqueIndex 3種、複数挿入はバッチ＋トランザクション。
  • Turso(libSQL) クライアントは db/client.ts でシングルトン化。リクエスト毎の再生成がない。dynamic import で初期JSを抑制している箇所もある。
